# AGENTS.md

Dotfiles for macOS 27 and for an Ubuntu 26.04 desktop used over SSH. These are the OS releases supported and tested. `setup.sh` installs tools and configs; `ai_tools/setup.sh` sets up Claude Code, the Claude desktop app, Codex, T3 Code, and the skills in `ai_tools/skills`.

- **Steps.** Both runners only run steps. A step is an `install.sh` beside the files it installs (the two `manual-steps.sh` are the exceptions). Each one sources `lib/common.sh` through `${BASH_SOURCE[0]}`, so it works when run directly and when sourced, and calls `main` only when run directly. Helper files a step sources, from `<step>/lib/` or, when several AI tool steps share them, `ai_tools/lib/`, define functions, constants, and tables, and run nothing.
  - **Shape.** A step defines `status` and `apply`. The default `main` in `lib/common.sh` checks the arguments with `step_args`, then runs `status` under `--status` and `apply` otherwise. `status` is a read-only report that runs the step's own checks through the `status_*` helpers and ends with `status_result`. Under `--quick`, `status_quick` succeeds, and the step skips its slowest checks.
  - **Config-only steps.** A `*_files` function passes each config file the step copies, as source and destination, to the function it's given. `apply` is `copy_step "<message>" <files-fn>`, and `status` is `copy_status <files-fn>`. `editorconfig/install.sh` is the template, and `vim/install.sh` shows a step that also does more.
  - **sudo changes.** `sudo_item` and the helpers for root-owned files and third-party apt repos live in `lib/system.sh`, which a script that uses them sources right after `lib/common.sh`. A step that changes the system with sudo lists each simple item once, with `sudo_item "<status text>" "<pending text>" <check-fn> <fix-fn>`, in a function that `status` and `apply` both call and that starts with `sudo_items_reset`. `sudo_items_pending`, `sudo_items_apply`, and `sudo_items_status` drive every item, or only those whose check functions they're given, so an item that branches stays custom code in its place. `ubuntu/install.sh` and `docker/install.sh` show it.
- **New step.**
  1. Add it to the runner's `MACOS_STEPS`, `UBUNTU_STEPS`, or both.
  2. Write `<step>/install.sh`: a header, its `*_files` functions, `status`, and `apply`.
  3. Add a test in `tests/`. A step that only copies configs joins the list in `tests/test-config-steps.sh`.
  4. Update the docs that **Docs change with the code** names.
- **Copied, not linked.** Setup copies configs and skills into `$HOME`, so a repo edit takes effect only when its step re-runs. Run the scripts or touch `$HOME` only when asked: they change the real machine. `--status` (`just status`) only reads, so use it to see what's set up.
- **Testing a step by hand.** Read the step's header first: it says whether the step changes the system whatever `HOME` is, and where to test it instead. Run a macOS step that changes the system on this Mac only when asked. Otherwise run the step with a temp `HOME` and `TMUX_TMPDIR`, stdin from `/dev/null`, and the variables that send a step's writes outside `HOME` unset: `T="$(mktemp -d)"; env -u XDG_CONFIG_HOME -u XDG_STATE_HOME -u XDG_DATA_HOME -u XDG_CACHE_HOME -u MISE_DATA_DIR -u MISE_CONFIG_DIR -u MISE_GLOBAL_CONFIG_FILE -u CODEX_HOME -u CLAUDE_CONFIG_DIR -u BASH_ENV HOME="$T" TMUX_TMPDIR="$T" bash setup.sh <step> </dev/null`. If your shell sets others that `setup_sandbox` in `tests/lib.sh` unsets, such as a `DOTFILES_*` variable, `GIT_DIR`, or `SSH_AUTH_SOCK`, unset them too. A second run changes nothing, and `--status` then reports nothing that needs attention, apart from what needs a person, such as the `git` step's GitHub login.
- **Per-machine stays out.** `copy_file` replaces a copied file whenever it differs from the repo's, with no backup or question, Zed's `settings.json` and `keymap.json` and the user instructions in `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` included. Other files that other tools also edit, such as shell startup files, `~/.ssh/config`, `~/.gitconfig`, and app settings, only get settings merged or the repo's own lines added; each startup file gets one line that sources a file the `zsh` step copies. Settings for one machine, such as commit signing (`git/setup-signing.sh`), get their own script that setup doesn't run.
- **Both OSes.** Every step can run on either OS. Branch on `is_macos` or `is_ubuntu` from `lib/common.sh` (`$OSTYPE` in zsh files), and skip with a message what one OS lacks. A step only one OS runs by default goes in that OS's `MACOS_STEPS` or `UBUNTU_STEPS`. Use apt and Ubuntu's paths directly, since no other distro is supported. To test on Ubuntu, run the step as a non-root user in an `ubuntu:26.04` container, which has 26.04's Rust coreutils, after `apt-get install sudo-rs`, or, for a step that needs systemd, in an Ubuntu VM such as an OrbStack machine.
- **Scripts** target `/bin/bash` 3.2, since `setup.sh` runs before Homebrew. Reuse the helpers in `lib/common.sh`. A step that breaks one of these rules says why in its header, as `homebrew` does.
  - Every step is idempotent: when already applied, it says so and changes nothing.
  - `confirm` says no without a terminal unless `DOTFILES_ASSUME_YES=1`. A declined `confirm` doesn't fail the step, which finishes sensibly.
  - A step carries no migration code for files older versions of this repo left, but keeps user edits.
  - A state that could still break something is reported by `--status`, or fails the step before it changes anything.
  - A missing prerequisite fails the step before it changes anything (`require_cmd <cmd> || return 1`). An optional integration is the exception: when only it lacks a command, such as Claude Code's worktree hook without `git wt`, the step sets up the rest, then fails, and status reports the integration missing.
  - A failed install fails the step after it does what else it can.
- **Verify** with `just check`, whose recipe lists what it runs, and `just test`, or `just test <name>...` for only the named tests. Before writing a test, read the headers of `tests/lib.sh`, `tests/sentinels.sh`, and `tests/run.sh` (timeouts, skips, and the `# os: macos` mark), and `setup_sandbox`. A test stubs every command in `SENTINELS` it reaches, and reuses the shared helpers, such as `git_commit`, `stub_login_shell_zsh`, and the Ubuntu fixtures in `tests/ubuntu-sandbox.sh`. CI (`.github/workflows/check.yml`) runs both on macOS and Ubuntu. `just test-ubuntu` runs a full setup in a throwaway OrbStack machine; run it only when asked. Only on a throwaway machine, `DOTFILES_ASSUME_YES=1` answers yes to every `confirm`, `DOTFILES_SSH_KEY_ONLY=1` turns off SSH password logins without a key login, and `DOTFILES_ALLOW_WORKTREE=1` installs the health alerts from a git worktree.
- **Docs change with the code**, in the same commit. `just check` fails when README's step table, package lists, or copy-back list, or `ai_tools/README.md`'s step list, disagree with the code, when the `claude-code` step writes a key `scripts/claude-settings-keys.txt` lacks, when a skill's invocation differs across its `SKILL.md`, `agents/openai.yaml`, and category README heading, or when a local link breaks in `README.md`, `ai_tools/README.md` (`scripts/check-docs.sh`), or the skills and their READMEs (`scripts/check-skills.sh`). Add a key to `scripts/claude-settings-keys.txt` only once you've checked it against Claude Code. No check covers these:
  - the Claude and Codex models the `claude-code` and `codex` steps set → the reviewer table in `ai_tools/skills/engineering/interrogate/SKILL.md`
  - an app's keys rechecked against a new version → the version table in `ai_tools/README.md` "Maintenance"
  - what the `ai_tools/setup.sh` steps do → the **(script)** marks in `ai_tools/README.md`
  - `upgrade` → README "Updating"; `upgrade-ai-tools` → `ai_tools/README.md` "Updating"
  - steps done by hand → the "Manual steps" section of README or `ai_tools/README.md`. The `manual-steps` steps print it at run time, so it's the only copy.

  `README.md` and `ai_tools/README.md` each start with a first-run checklist per OS, and keep to what a user does and sees. How a step handles a case goes in a comment beside the code that handles it, or in a test. Run prose through `unslop`.
- **Skills**: load `writing-for-agents` before editing one or this file. Most are modified upstream copies (the skills README's Acknowledgements lists which), so port upstream diffs by hand and keep our changes.
