# AGENTS.md

Dotfiles for macOS and for an Ubuntu 26.04 desktop used over SSH. Ubuntu is the only Linux supported: 26.04 is the release to test on, and 24.04 is best effort. `setup.sh` installs tools and configs; `ai_tools/setup.sh` sets up Claude Code, the Claude desktop app, Codex, T3 Code, and the skills in `ai_tools/skills`.

- **Steps.** Both runners only run steps. A step is an `install.sh` beside the files it installs (the two `manual-steps.sh` are the exceptions). Each one sources `lib/common.sh` through `${BASH_SOURCE[0]}`, so it works when run directly and when sourced, and calls `main` only when run directly. A step may also source helper files from `<step>/lib/` the same way, as `ubuntu` does; they only define functions. `main` starts with `step_args "$@"`, which handles `--help` and rejects any other argument but the shared flags, then hands `--status`, wherever `status_requested "$@"` finds it, to the step's `status` function, a read-only report that runs the step's own checks through the `status_*` helpers. A new step goes in the runner's `MACOS_STEPS` or `UBUNTU_STEPS`, or both, which `step_script` in `lib/common.sh` resolves to `<step>/install.sh` beside the runner, and gets a `status` and a test in `tests/` too. A step that only copies configs joins the list in `tests/test-config-steps.sh`. `vim/install.sh` is the shape to copy for a new step: its `*_files` functions list the files it copies, and its `status` reports each thing it sets up.
- **Copied, not linked.** Setup copies configs into `$HOME`, and copies skills once into `~/.agents/skills`, where `~/.claude/skills/<name>` links to each copy, so a repo edit takes effect only when its step re-runs. Run the scripts or touch `$HOME` only when asked: they change the real machine. `--status` (`just status`) only reads, so use it to see what's set up. To test a step, run it with `HOME` set to a temp dir, every `XDG_*` variable unset, and stdin from `/dev/null`: `T="$(mktemp -d)"; env -u XDG_CONFIG_HOME -u XDG_STATE_HOME -u XDG_DATA_HOME -u XDG_CACHE_HOME HOME="$T" TMUX_TMPDIR="$T" bash setup.sh <step> </dev/null`. A second run changes nothing, and `--status` then reports each item `ok`, `skipped`, or `unverified`, apart from what needs a person, such as the `git` step's GitHub login. Steps write under a set `XDG_*` directory instead of `HOME`, so a set `XDG_STATE_HOME` alone puts the record of installed files on the real machine. Some steps change the system whatever `HOME` is. A step's header says whether it does, and where to test it instead, so read the header before running the step. tmux's socket lives under `/tmp`, so also set `TMUX_TMPDIR` to a temp dir when a test runs tmux. Run a macOS step that changes the system on this Mac only when asked.
- **Per-machine stays out.** Files other tools also edit (`~/.zshrc`, `~/.zprofile`, `~/.zshenv`, `~/.profile`, `~/.ssh/config`, `~/.gitconfig`, app settings) get settings merged, or only the repo's own lines added, moved into place, or deduplicated. The file is never replaced, and its other lines stay as they are. `rewrite_lines_in_order` in the `zsh` step and `add_block` in `ssh/lib/hosts.sh`, which `ssh/add-host.sh` sources, insert above other lines on purpose, since order decides which value wins. Zed's `settings.json` and `keymap.json` are the exception: they're JSONC, and jq would drop their comments, so the `zed` step asks before replacing a copy edited in the app or by hand (`copy_file_ask`). Settings specific to one machine, such as commit signing (`git/setup-signing.sh`), get their own script that setup doesn't run.
- **Both OSes.** Every step runs on macOS and Ubuntu. Branch on `is_macos` or `is_ubuntu` from `lib/common.sh` (`$OSTYPE` in zsh files), and skip with a message what one OS lacks. A step only one OS runs by default goes in that OS's `MACOS_STEPS` or `UBUNTU_STEPS`. Use apt and Ubuntu's paths directly; there's no other distro to handle. To test on Ubuntu, run the step as a non-root user in an `ubuntu:26.04` container, which has Rust coreutils as a 26.04 install does, after `apt-get install sudo-rs` adds the sudo the image lacks, or in an Ubuntu VM that runs systemd, such as an OrbStack machine, for steps that need it.
- **Scripts** target `/bin/bash` 3.2, since `setup.sh` runs before Homebrew. Every step is idempotent: when already applied, say so and change nothing, and finish sensibly when `confirm` says no (it does without a terminal unless `DOTFILES_ASSUME_YES=1`). A step assumes a machine set up from the current version, so it carries no migration from earlier versions and no guard against hand-made files or unsupported setups. A state that could still break something is reported by `--status`, or fails the step before it changes anything. A missing prerequisite fails the step before it changes anything (`require_cmd <cmd> || return 1`). An optional integration is the exception: when only it lacks a command, as Claude Code's worktree hook lacks `git wt` and the Ghostty snap lacks `snap`, the step sets up the rest, then fails, and status reports the integration missing. A failed install fails the step after it does what else it can. A declined `confirm` doesn't fail the step. A step that breaks one of these rules says why in its header, as `homebrew` does. Reuse the helpers in `lib/common.sh`.
- **Verify** with `just check` and `just test`. `just check` runs shellcheck at every severity, `zsh -n`, and the scripts the justfile's `check` recipe lists; each script's header says what it checks and needs. `just test` runs each `tests/test-*.sh` under `/bin/bash` in the sandbox `tests/lib.sh` sets up; read its header and `setup_sandbox` before writing a test. A test stubs every command in `SENTINELS` it reaches, since a sentinel that runs fails the test, and a command joins `SENTINELS` when a test would otherwise reach one that changes the real machine, uses the network, or reads real hardware or system state. A test ends with `test_done`, and calls `skip` when it lacks a tool it needs. CI (`.github/workflows/check.yml`) runs both on macOS and Ubuntu, and its comments say what else it checks. `just test-ubuntu` runs a full setup in a throwaway OrbStack machine; run it only when asked. Only on a throwaway machine, `DOTFILES_ASSUME_YES=1` answers yes to every `confirm`, `DOTFILES_SSH_KEY_ONLY=1` turns off SSH password logins without a key login, and `DOTFILES_ALLOW_WORKTREE=1` installs the health alerts from a git worktree.
- **Docs change with the code**, in the same commit:
  - brew packages → README "What's included"
  - `setup.sh`'s `MACOS_STEPS` and `UBUNTU_STEPS` → README "How setup works", and `UBUNTU_STEPS` also the step list in README "Ubuntu"
  - new config files → the step's `*_files` functions and README "Maintenance" copy-back list
  - new keys the `claude-code` step writes → `scripts/claude-settings-keys.txt`, once checked against Claude Code
  - `ai_tools/setup.sh` steps → `ai_tools/README.md`, marked **(script)**
  - `upgrade` → README "Updating"; `upgrade-ai-tools` → `ai_tools/README.md` "Updating"; a new stage of either → `stage_doc` in `scripts/check-docs.sh`
  - a full verification round → a new section at the top of `COMPATIBILITY.md`
  - steps done by hand → the "Manual steps" section of README or `ai_tools/README.md`. The `manual-steps` steps print it at run time, so it's the only copy.

  `README.md` and `ai_tools/README.md` each start with a first-run checklist per OS, and keep to what a user does and sees. How a step handles a case goes in a comment beside the code that handles it, or in a test. Run prose through `unslop`.
