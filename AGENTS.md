# AGENTS.md

Dotfiles for macOS 27 and for an Ubuntu 26.04 desktop used over SSH. These are the OS releases supported and tested. `setup.sh` installs tools and configs; `ai_tools/setup.sh` sets up Claude Code, the Claude desktop app, Codex, T3 Code, and the skills in `ai_tools/skills`.

- **Steps.** Both runners only run steps. A step is an `install.sh` beside the files it installs (the two `manual-steps.sh` are the exceptions). Each one sources `lib/common.sh` through `${BASH_SOURCE[0]}`, so it works when run directly and when sourced, and calls `main` only when run directly. Helper files a step sources, from `<step>/lib/` or, when several AI tool steps share them, `ai_tools/lib/`, define functions, constants, and tables, and run nothing.
  - **Shape.** A step defines `status` and `apply`. The default `main` in `lib/common.sh` checks the arguments with `step_args`, then runs `status` under `--status` and `apply` otherwise. `status` is a read-only report that runs the step's own checks through the `status_*` helpers and ends with `status_result`. Under `--quick`, `status_quick` succeeds, and the step skips its slowest checks.
  - **Config-only steps.** A `*_files` function passes each config file the step copies, as source and destination, to the function it's given. `apply` is `copy_step "<message>" <files-fn>`, and `status` is `copy_status <files-fn>`. `editorconfig/install.sh` is the template, and `vim/install.sh` shows a step that also does more.
  - **Items.** A step lists each simple thing it sets up once, with `item [--sudo] [--hint <text>] "<status text>" "<pending text>" <check-fn> <fix-fn>` from `lib/common.sh`, in a function that `status` and `apply` both call and that starts with `items_reset`. `items_status`, `items_ok`, `items_pending`, and `items_apply [--no-sudo]` drive every item, or only those whose check functions they're given, so an item that branches stays custom code in its place. `docker/install.sh` shows it.
  - **sudo changes.** The helpers for root-owned files and third-party apt repos live in `lib/system.sh`, which a script that uses them sources right after `lib/common.sh`, as it does `lib/casks.sh` for the Homebrew cask helpers. A step marks each item whose fix needs sudo `--sudo`, and asks once with `confirm_sudo_changes` for the list `items_pending` builds.
- **New step.**
  1. Add it to the runner's `MACOS_STEPS`, `UBUNTU_STEPS`, or both.
  2. Write `<step>/install.sh`: a header whose first line is one sentence saying what the step does, which `--help` lists, then its `*_files` functions, `status`, and `apply`.
  3. Add a test in `tests/`. A step that only copies configs joins the list in `tests/test-config-steps.sh`.
  4. Update the docs that **Docs change with the code** names.
- **Copied, not linked.** Setup copies configs into `$HOME`, so a repo edit takes effect only when its step re-runs, and `just copy-back` copies the installed configs that differ back into the repo. Every function whose name ends in `_files` is a `*_files` function to it, so give no other function such a name. Run the scripts or touch `$HOME` only when asked: they change the real machine. `--status` (`just status`) only reads, so use it to see what's set up.
- **Testing a step by hand.** Read the step's header first: it says whether the step changes the system whatever `HOME` is, and where to test it instead. Run a macOS step that changes the system on this Mac only when asked. Otherwise run the step with a temp `HOME` and `TMUX_TMPDIR`, stdin from `/dev/null`, and the variables that send a step's writes outside `HOME` unset: `T="$(mktemp -d)"; env -u XDG_CONFIG_HOME -u XDG_STATE_HOME -u XDG_DATA_HOME -u XDG_CACHE_HOME -u MISE_DATA_DIR -u MISE_CONFIG_DIR -u MISE_GLOBAL_CONFIG_FILE -u CODEX_HOME -u CLAUDE_CONFIG_DIR -u BASH_ENV HOME="$T" TMUX_TMPDIR="$T" bash setup.sh <step> </dev/null`. If your shell sets others that `setup_sandbox` in `tests/lib.sh` unsets, such as a `DOTFILES_*` variable, `GIT_DIR`, or `SSH_AUTH_SOCK`, unset them too. A second run changes nothing, and `--status` then reports nothing that needs attention, apart from what needs a person, such as the `git` step's GitHub login.
- **Per-machine stays out.** `copy_file` replaces a copied file whenever it differs from the repo's, with no backup or question, Zed's `settings.json` and `keymap.json` and the user instructions in `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` included. Other files that other tools also edit, such as shell startup files, `~/.ssh/config`, `~/.gitconfig`, and app settings, only get settings merged or the repo's own lines added; each startup file gets one line that sources a file the `zsh` step copies. Only a merge into such a file offers a backup first, through `maybe_backup`, which `--backup` and `--no-backup` answer. Settings for one machine, such as commit signing (`git/setup-signing.sh`), get their own script that setup doesn't run.
- **Both OSes.** Every step can run on either OS. Branch on `is_macos` or `is_ubuntu` from `lib/common.sh` (`$OSTYPE` in zsh files), and skip with a message what one OS lacks. A step only one OS runs by default goes in that OS's `MACOS_STEPS` or `UBUNTU_STEPS`. A step only one OS supports sets `STEP_OS=macos` or `STEP_OS=ubuntu` near its top, and the default `main` and `run_steps` skip it on the other OS, as `chrome/install.sh` shows. Use apt and Ubuntu's paths directly, since no other distro is supported. To test on Ubuntu, run the step as a non-root user in an `ubuntu:26.04` container, which has 26.04's Rust coreutils, after `apt-get install sudo-rs`, or, for a step that needs systemd, in an Ubuntu VM such as an OrbStack machine.
- **Scripts** target `/bin/bash` 3.2, since `setup.sh` runs before Homebrew. Reuse the helpers in `lib/common.sh`. A step that breaks one of these rules says why in its header, as `homebrew` does.
  - Every step is idempotent: when already applied, it says so and changes nothing.
  - `confirm` says no without a terminal unless `DOTFILES_ASSUME_YES=1`. A declined `confirm` doesn't fail the step, which finishes sensibly.
  - A step carries no migration code for files older versions of this repo left, but keeps user edits to the files it merges settings into.
  - A state that could still break something is reported by `--status`, or fails the step before it changes anything.
  - A missing prerequisite fails the step before it changes anything (`require_cmd <cmd> || return 1`), and the step names the step that installs it on its `STEP_NEEDS="homebrew"` line, so `run_steps` skips it when that step failed. An optional integration is the exception: when only it lacks a command, such as Claude Code's worktree hook without `git wt`, the step sets up the rest, then fails, and status reports the integration missing.
  - A failed install fails the step after it does what else it can.
- **Verify** with `just check`, whose recipe lists what it runs, and `just test`, or `just test <name>...` for only the named tests. Before writing a test, read the headers of `tests/lib.sh`, `tests/sentinels.sh`, and `tests/run.sh` (timeouts, skips, and the `# os: macos` and `# serial` marks), and `setup_sandbox`. A test stubs every command in `SENTINELS` it reaches, changes a repo function only through `replace_fn`, `as_os`, or `answer`, and reuses the shared helpers, such as `git_commit`, `stub_login_shell_zsh`, and the Ubuntu fixtures in `tests/ubuntu-sandbox.sh`. It changes a loaded script's function with `replace_fn`, the OS with `as_os macos|ubuntu`, and `confirm`'s answer with `answer yes|no`. A test whose timing can flake under load gets a `# serial` line, so it runs alone. CI (`.github/workflows/check.yml`) runs both on macOS and Ubuntu. Live Homebrew and AI compatibility checks run weekly, manually, and when their inputs change; the T3 schema check runs once per selected run. `just test-ubuntu` runs a full setup in a throwaway OrbStack machine; run it only when asked. Only on a throwaway machine, `DOTFILES_ASSUME_YES=1` answers yes to every `confirm`, `DOTFILES_SSH_KEY_ONLY=1` turns off SSH password logins without a key login, and `DOTFILES_ALLOW_WORKTREE=1` installs the health alerts from a git worktree.
- **Docs change with the code**, in the same commit. `just check` fails when README's step table or `ai_tools/README.md`'s step list disagrees with the runners, when a step's header line isn't one sentence of at most 90 characters, or when a local link breaks in `README.md` or `ai_tools/README.md` (`scripts/check-docs.sh`). It fails when a skill's frontmatter, name, description, or `agents/openai.yaml` is missing or malformed, when its invocation differs across its `SKILL.md`, `agents/openai.yaml`, and category README heading, or when a link breaks in the skills or their READMEs (`scripts/check-skills.sh`). It also fails when the `claude-code` step writes a key `scripts/claude-settings-keys.txt` lacks. Add a key to `scripts/claude-settings-keys.txt` only once you've checked it against Claude Code. No check covers these:
  - the Claude and Codex models the `claude-code` and `codex` steps set → the reviewer table in `ai_tools/skills/engineering/interrogate/SKILL.md`
  - an app's keys rechecked against a new version → the version table in `ai_tools/README.md` "Maintenance"
  - what the `ai_tools/setup.sh` steps do → the **(script)** marks in `ai_tools/README.md`
  - `upgrade` → README "Updating"; `upgrade-ai-tools` → `ai_tools/README.md` "Updating"
  - steps done by hand → the "Manual steps" section of README or `ai_tools/README.md`. The `manual-steps` steps print it at run time, so it's the only copy.

  `README.md` and `ai_tools/README.md` each start with a first-run checklist per OS, and keep to what a user does and sees. How a step handles a case goes in a comment beside the code that handles it, or in a test. Run prose through `unslop`.
- **Skills**: load `writing-for-agents` before editing one or this file. Most skills are modified upstream copies (the skills README's Acknowledgements lists which), so port upstream diffs by hand and keep our changes. The `skills` step owns `~/.agents/skills` and `~/.claude/skills`: it copies each repo skill into the first, links it from the second, and deletes every other entry in both, apart from Claude Code's own `synced` and dot-entries in `~/.claude/skills`.

## Code layout

Projects live at `~/Dev/<group>/<project>`, grouped by language or purpose, such as `~/Dev/go/envl`. This repo is at `~/Dev/setup/dotfiles`. `ts` in zsh and `prefix+f` in tmux pick a project from `~/Dev/*/*` and open a tmux session for it.

Worktrees go beside the projects, not inside them. Each tool keeps its own:

| Tool | Worktrees |
| :- | :- |
| `git wt`, the `implement` skill, and Claude Code's `--worktree`, subagents, and background sessions | `~/.worktrees/<group>/<project>/<name>`, or `~/.worktrees/_/<project>-<hash>/<name>` for a repo outside `~/Dev/<group>/<project>` |
| T3 Code | `~/.t3/worktrees/<repo>/<worktree>` |
| The Codex app | `~/.codex/worktrees` |
