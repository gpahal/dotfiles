# AGENTS.md

Dotfiles for macOS 27 and for an Ubuntu 26.04 desktop used over SSH. These are the OS releases supported and tested. `setup.sh` installs tools and configs; `ai_tools/setup.sh` sets up Claude Code, the Claude desktop app, Codex, T3 Code, and the skills in `ai_tools/skills`.

- **Steps.** Both runners only run steps. A step is an `install.sh` beside the files it installs (the two `manual-steps.sh` are the exceptions). Each one sources `lib/common.sh` through `${BASH_SOURCE[0]}`, so it works when run directly and when sourced, and calls `main` only when run directly. A step may also source helper files from `<step>/lib/`, as `git` and `ubuntu` do, or from `ai_tools/lib/` when several AI tool steps share them; they define functions, constants, and the tables their functions fill, and run nothing.
  - **Shape.** A step defines `status` and `apply`. The default `main` in `lib/common.sh` runs `step_args "$@"`, which handles `--help` and rejects any other argument but the shared flags, then calls `status` when `status_requested "$@"` finds `--status`, and `apply` otherwise. A step that needs more defines its own `main`, which starts with `step_args "$@"` and replaces the default. `status` is a read-only report that runs the step's own checks through the `status_*` helpers and ends with `status_result`. Under `--quick`, `status_quick` succeeds, and the step skips its slowest checks.
  - **Config-only steps.** A `*_files` function passes each config file the step copies, as source and destination, to the function it's given. `apply` is `copy_step "<message>" <files-fn>`, and `status` is `copy_status <files-fn>`. `editorconfig/install.sh` is the template, and `vim/install.sh` shows a step that also does more.
  - **sudo changes.** A step that changes the system with sudo lists each simple item once, with `sudo_item "<status text>" "<pending text>" <check-fn> <fix-fn>`, in a function that `status` and `apply` both call and that starts with `sudo_items_reset`. `sudo_items_pending`, `sudo_items_apply`, and `sudo_items_status` drive every item, or only the items whose check functions they're given, so an item that branches stays custom code in its place among the rest. `ubuntu/install.sh` and `docker/install.sh` use it.
- **New step.**
  1. Add it to the runner's `MACOS_STEPS`, `UBUNTU_STEPS`, or both, which `step_script` in `lib/common.sh` resolves to `<step>/install.sh` beside the runner.
  2. Write `<step>/install.sh`: a header, its `*_files` functions, `status`, and `apply`.
  3. Add a test in `tests/`. A step that only copies configs joins the list in `tests/test-config-steps.sh`.
  4. Update the docs that **Docs change with the code** names.
- **Copied, not linked.** Setup copies configs into `$HOME`, and copies skills once into `~/.agents/skills`, where `~/.claude/skills/<name>` links to each copy, so a repo edit takes effect only when its step re-runs. Run the scripts or touch `$HOME` only when asked: they change the real machine. `--status` (`just status`) only reads, so use it to see what's set up.
- **Testing a step by hand.** Run it with `HOME` set to a temp dir, every `XDG_*` variable unset, and stdin from `/dev/null`: `T="$(mktemp -d)"; env -u XDG_CONFIG_HOME -u XDG_STATE_HOME -u XDG_DATA_HOME -u XDG_CACHE_HOME HOME="$T" TMUX_TMPDIR="$T" bash setup.sh <step> </dev/null`. A second run changes nothing, and `--status` then reports each item `ok`, `skipped`, `unverified`, or `info`, apart from what needs a person, such as the `git` step's GitHub login. Steps write under a set `XDG_*` directory instead of `HOME`, so a set `XDG_STATE_HOME` alone puts the record of installed files on the real machine. Some steps change the system whatever `HOME` is. A step's header says whether it does, and where to test it instead, so read the header before running the step. tmux's socket lives under `/tmp`, so also set `TMUX_TMPDIR` to a temp dir when a test runs tmux. Run a macOS step that changes the system on this Mac only when asked.
- **Per-machine stays out.** Files other tools also edit (`~/.zshrc`, `~/.zprofile`, `~/.zshenv`, `~/.profile`, `~/.ssh/config`, `~/.gitconfig`, app settings) get settings merged, or only the repo's own lines added, moved into place, or deduplicated. The file is never replaced, and its other lines stay as they are. Each startup file the `zsh` step sets up gets one line that sources a file it copies: `~/.zprofile`, and on Ubuntu `~/.zshenv`, source `zsh/path.zsh`, which sets PATH for zsh, and on Ubuntu `~/.profile` sources `zsh/profile.sh`. `add_block` in `ssh/lib/hosts.sh`, which `ssh/add-host.sh` sources, inserts above other lines on purpose, since order decides which value wins. Two kinds of file are replaced whole, and `copy_file_ask` asks before replacing a copy edited in the app or by hand: Zed's `settings.json` and `keymap.json`, which are JSONC that jq would strip of comments, and the user instructions copied to `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`. Settings specific to one machine, such as commit signing (`git/setup-signing.sh`), get their own script that setup doesn't run.
- **Both OSes.** Every step can run on either OS. Branch on `is_macos` or `is_ubuntu` from `lib/common.sh` (`$OSTYPE` in zsh files), and skip with a message what one OS lacks. A step only one OS runs by default goes in that OS's `MACOS_STEPS` or `UBUNTU_STEPS`. Use apt and Ubuntu's paths directly; there's no other distro to handle. To test on Ubuntu, run the step as a non-root user in an `ubuntu:26.04` container, which has Rust coreutils as a 26.04 install does, after `apt-get install sudo-rs` adds the sudo the image lacks, or in an Ubuntu VM that runs systemd, such as an OrbStack machine, for steps that need it.
- **Scripts** target `/bin/bash` 3.2, since `setup.sh` runs before Homebrew. Reuse the helpers in `lib/common.sh`. A step that breaks one of these rules says why in its header, as `homebrew` does.
  - Every step is idempotent: when already applied, it says so and changes nothing.
  - `confirm` says no without a terminal unless `DOTFILES_ASSUME_YES=1`. A declined `confirm` doesn't fail the step, which finishes sensibly.
  - A step assumes a machine set up from the current version, so it carries no migration code for files left by older versions of this repo. User edits are still preserved.
  - A state that could still break something is reported by `--status`, or fails the step before it changes anything.
  - A missing prerequisite fails the step before it changes anything (`require_cmd <cmd> || return 1`). An optional integration is the exception: when only it lacks a command, as Claude Code's worktree hook lacks `git wt` and the Ghostty snap lacks `snap`, the step sets up the rest, then fails, and status reports the integration missing.
  - A failed install fails the step after it does what else it can.
- **Verify** with `just check` and `just test`. `just check` runs shellcheck at every severity, a grep for bash 4 syntax, `zsh -n`, and the scripts the justfile's `check` recipe lists; each script's header says what it checks and needs. `just test` runs each `tests/test-*.sh` under `/bin/bash` in the sandbox `tests/lib.sh` sets up, and `just test <name>...` runs only the named ones; read its header and `setup_sandbox` before writing a test. A test stubs every command in `SENTINELS` it reaches, since a sentinel that runs fails the test, and a command joins `SENTINELS` when a test would otherwise reach one that changes the real machine, uses the network, or reads real hardware or system state. A test ends with `test_done`, and calls `skip` when it lacks a tool it needs. CI (`.github/workflows/check.yml`) runs both on macOS and Ubuntu, and its comments say what else it checks. `just test-ubuntu` runs a full setup in a throwaway OrbStack machine; run it only when asked. Only on a throwaway machine, `DOTFILES_ASSUME_YES=1` answers yes to every `confirm`, `DOTFILES_SSH_KEY_ONLY=1` turns off SSH password logins without a key login, and `DOTFILES_ALLOW_WORKTREE=1` installs the health alerts from a git worktree.
- **Docs change with the code**, in the same commit:
  - brew packages → README "What's included"
  - `homebrew/install.sh`'s `UBUNTU_CASKS` and `UBUNTU_PACKAGES`, and the Brewfile's Mac-only formulae → README "Ubuntu"
  - `setup.sh`'s `MACOS_STEPS` and `UBUNTU_STEPS` → README "How setup works", and `UBUNTU_STEPS` also the step list in README "Ubuntu"
  - new config files → the step's `*_files` functions and README "Maintenance" copy-back list
  - new keys the `claude-code` step writes → `scripts/claude-settings-keys.txt`, once checked against Claude Code
  - the Claude and Codex models the `claude-code` and `codex` steps set → the reviewer table in `ai_tools/skills/engineering/interrogate/SKILL.md`
  - an app's keys rechecked against a new version → the version table in `ai_tools/README.md` "Maintenance"
  - `ai_tools/setup.sh` steps → `ai_tools/README.md`, marked **(script)**
  - `upgrade` → README "Updating"; `upgrade-ai-tools` → `ai_tools/README.md` "Updating"; a new stage of either → `stage_doc`, and `stage_code` when its code differs, in `scripts/check-docs.sh`
  - steps done by hand → the "Manual steps" section of README or `ai_tools/README.md`. The `manual-steps` steps print it at run time, so it's the only copy.

  `README.md` and `ai_tools/README.md` each start with a first-run checklist per OS, and keep to what a user does and sees. How a step handles a case goes in a comment beside the code that handles it, or in a test. Run prose through `unslop`.
